What I'd flag as risk, roughly in priority order
1. Multi-tenancy is being deferred while the tenant-specific code keeps growing. Every week the hardcoded "Island Tacos", "it-dav7dwn8", 284-544-8088, @islandtacosbvi.com, BVI tax = 0, default IP 192.168.132.100, etc. spread into new code paths. The longer this goes, the more the eventual extraction looks like a rewrite. The store_settings table you mention should probably get scaffolded now and new features should be required to read from it, even if the only row in it is "Island Tacos." Otherwise you're paying interest on this debt every PR.

2. PIN-based admin auth is going to fail an enterprise security review. ADMIN_PIN / STAFF_PIN are shared secrets — can't be rotated per user, no per-actor audit trail, single factor, no lockout. Clerk is already in the stack and gated behind CLERK_SECRET_KEY. Migrating staff actions (refunds, shift open/close, settings) to Clerk-authenticated users with per-user PINs backed by their Clerk identity would give you a real audit log without changing the staff UX. The current model is fine for one trusted restaurant; it won't be sellable.

3. The download endpoints are a sprawling, inconsistent security surface. downloads.ts has ~10 routes mixing four different auth models: requireAdminAuth, PIN-in-body (new), localhost-only IP check, and unauthenticated. The /api/download/server route — which serves the actual server bundle — appears to be unauthenticated. Anyone who knows the URL can pull your compiled API server. Probably fine because it's also on GitHub, but it should be a deliberate decision documented next to the route, not an accident. Worth a one-pass consolidation: single middleware, explicit "public" allowlist, comment on every route explaining why its auth level is what it is.

4. No CI is the biggest leverage point. Two AI agents (me + Replit) push to the same main. There's no enforced typecheck, lint, audit, or test on push. Your "always re-verify" rule is social. A 15-line GitHub Actions workflow running pnpm run typecheck && pnpm audit --prod --audit-level=high && pnpm test on every push would catch the class of bugs that you can't catch by eye — and prevent the "Cursor pushed something Replit didn't notice broke" scenario. This is probably the single highest-ROI thing you could do this week.

5. Test coverage is unclear and the highest-stakes code is money handling. Cash transactions, refunds, shift Z-reports, ATH Móvil payment confirmation, sales export. I saw one critical-flows.test.ts referenced but no evidence it runs anywhere. For SaaS, "the POS lost a $23 cash refund" is the kind of bug that ends a customer relationship. A test pyramid that pins:

DB-level: shift balance math, refund accounting, discount edge cases
API-level: idempotency on POST /api/orders, double-charge prevention on payment routes
E2E: at least one walk-through of place-order → KDS → ready → SMS → pickup ...is worth more than any new feature right now.
6. The mini PC update flow is brittle for a fleet. UPDATE.bat → fetches latest server bundle → restarts pm2. Works for one mini PC; for 20 it's a footgun. No version pinning, no rollback, no health-check that confirms the new bundle actually starts, no checksum/signature verification of what you're downloading from orders.islandtacosbvi.com. If a bad bundle ever ships and the mini PC restarts itself onto it, you have an offline restaurant until someone drives to the shop. Worth adding: signed bundles, post-restart health probe with auto-rollback on failure, and a /api/version endpoint that the cloud can poll to know which version every tenant is on.

7. replit.md is doing too many jobs. It's the README, the architecture doc, the user-preferences doc, the accepted-risks log, and the agent context primer. It works today; in 6 months it'll be 600 lines and the AI agents will start missing things in it. Split into docs/architecture.md, docs/security.md, docs/runbook.md, docs/known-risks.md, and let replit.md be a 30-line index that points at them. Better anchors for both human contributors and AI agents.

8. Observability ends at logs. Pino + req.log is fine for cloud. But the mini PC failing silently (printer offline, SMS gateway unreachable, Postgres slow) is invisible until the owner notices an SMS didn't go out. For SaaS, you'll want at least: structured error reporting (Sentry or self-hosted equivalent) on both targets, and a heartbeat from each mini PC to cloud so the central admin site can show "tenant X has been offline for 14 minutes."

9. Two-agent push-to-main will eventually conflict. Right now it's working because volume is low. The first time Replit and I both touch the same file with different fixes in the same hour, someone's work disappears. A lightweight convention — cursor/* and replit/* branches for anything more than a one-line config change, with PRs that auto-rebase against main — gives you reversibility for free.
